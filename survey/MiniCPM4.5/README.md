## 概要

MiniCPM-V 4.5は、OpenBMBが開発した **8Bパラメータ** のマルチモーダル大規模言語モデル（MLLM）。高解像度画像・高フレームレート動画・文書OCRの理解を、極めて効率的な推論コストで実現する。

**特徴:**
- **統一3D-Resampler**: 画像・動画の両方に対応するPerceiver-Resampler。画像に対しては最大16倍、動画に対してはさらに6倍の時間圧縮を実現（合計96倍）
- **統一文書学習パラダイム**: テキスト領域に動的ノイズを付与し、OCR・文書知識獲得・文脈推論を単一目的関数に統合
- **ハイブリッドRL戦略**: 短い推論モードと長い推論モードを交互にロールアウトし、GRPOで同時最適化
- **8Bパラメータで GPT-4o-latest や Qwen2.5-VL 72B を凌駕**（OpenCompass 77.0）

**タスク:**
- 高解像度画像理解（任意アスペクト比）
- 高フレームレート・長時間動画理解
- 文書OCR・知識獲得
- 数学・科学・推論（短/長推論モード）
- マルチイメージ推論

**性能（主要ベンチマーク）:**

| ベンチマーク | MiniCPM-V 4.5 (8B) | Qwen2.5-VL 72B | GPT-4o |
|---|---|---|---|
| OpenCompass | **77.0** | 76.1 | 75.4 |
| OCRBench | **89.0** | 88.2 | 82.2 |
| Video-MME (w/ sub) | 73.5 | **79.1** | 77.2 |
| MathVista | **79.9** | 74.2 | 71.6 |
| MMMU | **67.7** | 68.2 | 72.9 |
| VideoMME推論時間 | **0.26h** | 3.00h | - |
| VideoMMEメモリ | **28G** | 60G | - |

## MiniCPM-V 4.5の主要イノベーション

### 1. **統一3D-Resampler**
**問題**: 既存MLLMは高解像度画像に256トークン（448x448）、短い動画に1,536〜3,072トークンを消費し、GPU計算量が膨大

**解決**: 2D-Resamplerを3Dに拡張し、空間・時間の冗長性を同時に圧縮
- **画像**: 各スライスをcross-attentionで`Q`トークンに圧縮（例: 448x448 → 64トークン、最大16倍圧縮）
- **動画**: 隣接フレームをパッケージ化し、3D cross-attentionでさらに6倍の時間圧縮
- 学習可能クエリ + 2D空間位置埋め込み + 1D時間位置埋め込み

**効果**:
- 6秒2fps 448x448動画 = わずか128視覚トークン（他のMLLMの12〜24分の1）
- VideoMME: 推論時間 0.26h（Qwen2.5-VL 7Bの3.00hの8.7%）、メモリ28G
- 画像・動画で同一の重みを共有 → 画像知識が動画に転移

**実装**: `resampler.py`

### 2. **統一文書学習パラダイム（動的ビジュアルコラプション）**
**問題**: 文書PDFの知識獲得は外部パーサーに依存し、ノイズが多い。OCR学習は過度な拡張で幻覚を生む

**解決**: 文書画像のテキスト領域に動的レベルのノイズ（コラプション）を付与し、原文を復元させる単一目的関数
- **低コラプション**: テキストが視認可能 → OCR認識力を強化
- **中コラプション**: テキストが曖昧 → 視覚的手がかりと文脈の統合推論
- **高コラプション**: テキストが完全マスク → 文書レイアウト・図表・内部知識からの推論

**効果**:
- MMMU +2.4pt、AI2D +1.6pt、OCRBench +41pt（外部パーサー方式比較）
- 脆弱なパーサー不要、データエンジニアリング軽減

**実装**: `training_data.py`（`DocumentCorruptionAugment`クラス）

### 3. **ハイブリッド強化学習（Hybrid RL）**
**問題**: 長い推論モードのみの学習はトークン消費が大きく、短い応答の効率が悪化

**解決**: ロールアウト時に短い/長い推論モードをランダムに交互実行し、GRPOで同時最適化
- KL損失・エントロピー損失なし（安定性向上）
- 50%のプロンプトを長い推論モードに割り当て
- 短い推論の「直接性」が長い推論の効率を改善、長い推論の「分析力」が短い推論を強化

**効果**:
- OpenCompass 77.1（long-only: 77.0、short-only: 76.0）
- 学習トークン消費: 3.1B（long-only: 4.4Bの70.5%）

**実装**: `loss_and_training.py`（`HybridRLTrainer`クラス）

### 4. **報酬品質管理（Reward Quality Control）**
**問題**: ルールベース検証は単純な回答のみ対応可能。確率ベース報酬は一般ドメインに強いが不安定

**解決**: 両方を組み合わせたハイブリッド報酬
- **ルールベース報酬**: 短い回答（数値等）に98%精度で適用
- **確率ベース報酬（RLPR）**: 自然言語回答に対する汎用検証
- **嗜好報酬**: Reward Modelで最終回答部分のみ評価（長い推論の思考過程は無視）
- **最終報酬**: `R = R_acc + R_format + R_rep + 0.5 * R̃_rm`

**実装**: `loss_and_training.py`（`compute_hybrid_reward`関数）

### 5. **RLAIF-V（幻覚低減）**
**問題**: MLLMは視覚入力と矛盾する情報を生成する（幻覚問題）

**解決**: スケーラブルなAIフィードバックによる選好学習
- 複数回答をサンプリング → 検証可能な原子的主張に分解 → 主張レベルの事実検証
- 事実誤りが少ない回答を選好 → DPOで学習

**効果**:
- HallusionBench 61.2（他モデル50前後）
- ObjHalBench、MMHal-Benchでも優位

**実装**: `loss_and_training.py`（`RLAIFVTrainer`クラス）

### 6. **LLaVA-UHD画像パーティショニング**
**問題**: 高解像度・任意アスペクト比の画像を固定サイズのViTに入力する必要がある

**解決**: 画像を最適なグリッドに分割し、各スライスを個別にエンコード
- 画像のアスペクト比に最も近いグリッド（例: 2x3）を選択
- 各スライスを`scale_resolution`（例: 448x448）にリサイズ
- ソース画像（全体縮小版）+ 各スライスをそれぞれResamplerに入力

**実装**: `vision_encoder.py`（`slice_image`関数）, `training_data.py`

## 処理フロー詳細

### 推論フロー

```
1. 入力準備
   ├── 画像: PIL Image → slice_image() でスライス分割
   │   ├── ソース画像: (3, H_src, W_src)  ※最適サイズにリサイズ
   │   └── スライス群: N_slices × (3, H_slice, W_slice)
   ├── 動画: フレーム群 → パッケージに分割 (pkg_size フレーム/パッケージ)
   │   └── パッケージ群: T_pkg × (F, 3, H, W)
   └── テキスト: 会話 → トークン化、<im_start><im_patch>*Q<im_end> を挿入

2. 視覚エンコーディング
   ├── 各スライス/フレーム → EVA02/SigLip
   │   └── (N, 3, H, W) → (N, L_vis, D_vis)   L_vis=(H/14)*(W/14), D_vis=1792
   └── CLS/prefix トークン除去

3. Resampler圧縮
   ├── 画像(2D): (N_slices, L_vis, D_vis) → (N_slices, Q, D_llm)
   │   Q=64, D_llm=4096
   └── 動画(3D): (T_pkg, F*L_vis, D_vis) → (T_pkg, Q, D_llm)
       └── 時間位置埋め込みで各フレームの時間位置をエンコード

4. マルチモーダル融合
   ├── テキスト: input_ids → embed_tokens → (B, L_text, D_llm)
   ├── 視覚: (N_total, Q, D_llm) をバッチ内の対応画像に割り当て
   └── <im_patch> プレースホルダを視覚埋め込みで置換
       → (B, L_total, D_llm)   L_total = L_text - N_img*Q + N_img*Q (サイズ同一)

5. LLMデコーダ
   └── (B, L_total, D_llm) → Mistral/Qwen2 Transformer → (B, L_total, V)

6. テキスト生成
   ├── 短い推論モード: 直接回答
   └── 長い推論モード: <think>...</think> + 回答
```

### 学習フロー

```
事前学習 (3段階)
├── Stage 1: Resampler のみ学習（他はフリーズ）
│   └── データ: 画像-キャプション対
├── Stage 2: 視覚エンコーダ + Resampler 学習（LLMフリーズ）
│   └── データ: OCRリッチデータ + 画像-キャプション対
└── Stage 3: 全パラメータ End-to-End 学習
    └── データ: テキストのみ、画像-テキストインターリーブ、動画、文書

SFT (2段階)
├── Stage 1: 汎用SFT
│   └── データ: 高品質指示-応答データ + 10%テキストのみデータ
└── Stage 2: Long-CoT & 3D-Resampler
    └── データ: Long-CoT指示 + 高フレームレート動画
    └── 2D→3D Resampler アーキテクチャ拡張

RL (ハイブリッド)
├── GRPO: 短い/長い推論モードのランダム交互ロールアウト
│   └── 報酬: R_acc + R_format + R_rep + 0.5 * R̃_rm
└── RLAIF-V: DPO による幻覚低減

学習設定:
├── 事前学習 LR: 5e-5 (WSD スケジューラ)
├── SFT LR: 1e-5 → 1e-6 (cosine decay)
├── RL LR: 1e-6 (固定)
├── GRPO: batch=128プロンプト×8応答, max_len=8192, temp=1.0
└── RLAIF-V: batch=256, β=0.1, 400ステップ
```

| テンソル | 形状 | 説明 |
|---|---|---|
| 入力画像 | `(3, H, W)` | RGB画像。H, Wはpatch_size(14)の倍数 |
| 画像スライス群 | `(N_slices, 3, H_s, W_s)` | パーティション後のスライス。N_slicesは1〜max_slice_nums+1 |

| 記号 | 意味 | 典型値 |
|---|---|---|
| `B` | バッチサイズ | 1〜4 (GPU依存) |
| `N` / `N_slices` | 画像スライス数 | 1〜10 |
| `T_pkg` | 動画パッケージ数 | 動画長/pkg_size |
| `F` | パッケージ内フレーム数 | 3〜6 |
| `L_vis` | ViT出力のパッチトークン数 | (H/14)*(W/14)、例: 1024 |
| `Q` | Resamplerのクエリ数 | 64 (grid_size=8) |

| `H_head` | アテンションヘッドの次元 | 128 |
| `N_heads` | アテンションヘッド数 | 32 (D_llm / H_head) |

## FAQ

### Q1. なぜResamplerを3Dに拡張するのか？2D-Resamplerのままではダメなのか？

2D-Resamplerは各フレームを独立に圧縮するため、動画のフレーム数に比例してトークンが増加する。例えば、6秒2fps (12フレーム) の448x448動画は `12 × 64 = 768` トークンになる。3D-Resamplerは隣接フレームをパッケージ化して共同圧縮するため、`2 × 64 = 128` トークンに削減できる（パッケージサイズ6の場合）。実験では、3D-Resamplerはトークン数3分の1で2Dより高い性能を達成している（Table 5: 72.5 vs 71.5 on VideoMME w/o sub）。

### Q2. 画像と動画で同じResamplerの重みを共有できるのか？

共有可能。Resamplerの核心はcross-attentionであり、入力特徴の空間的な形状に依存しない。画像は2D空間位置埋め込みのみ、動画はそれに加えて1D時間位置埋め込みを追加するだけで区別される。このため、画像で事前学習した2D-Resamplerを3D-Resamplerに軽量なSFTで拡張でき、画像の知識が動画に効率的に転移する。

### Q3. 統一文書学習パラダイムと従来のOCR学習の違いは？

従来のOCR学習は「クリーンな画像からテキストを読む」訓練のみ。過度なデータ拡張は幻覚を生む。MiniCPM-V 4.5の手法は、テキスト領域に3段階のノイズ（低/中/高コラプション）を動的に付与し、モデルに「テキストが見えるときはOCR」「見えないときは文脈推論」を自動切り替えさせる。これにより、OCR精度と文書知識獲得を単一の目的関数で同時に達成し、外部パーサーへの依存を完全に排除する。

### Q4. ハイブリッドRLはなぜ効果的なのか？

短い推論と長い推論は相補的な能力を提供する。長い推論で培われた「分析的深さ」が短い推論の精度を向上させ、短い推論で培われた「直接性・効率性」が長い推論の冗長性を抑制する。ハイブリッド戦略はこの相互強化を活用し、OpenCompass 77.1を達成（long-only: 77.0、short-only: 76.0）しながら、学習トークン消費をlong-onlyの70.5%に削減する。

### Q5. Reward Modelは長い推論モードの思考過程も評価するのか？

評価しない。RMは最終回答部分のみをスコアリングし、`<think>...</think>`内の思考過程は完全にスキップする。これは、標準的なRMが分布外の長い推論チェーンを正しく評価できず、学習の不安定性やアライメント品質の低下を招くためである。最終回答のみを評価することで、安定かつ密なフィードバックを提供できる。

### Q6. LLaVA-UHDのパーティショニングはどう動作するのか？

1. 入力画像の解像度から最適なスライス数を推定 (`ceil(W*H / scale_resolution^2)`)
2. 候補グリッド（例: 1x2, 2x1, 2x2, 1x3, ...）からアスペクト比が最も近いものを選択
3. 画像をグリッドに沿って分割し、各スライスを `scale_resolution` にリサイズ
4. ソース画像（全体の縮小版）も1つのスライスとして追加
5. 各スライスを独立にViT + Resamplerに入力

### Q7. 8Bパラメータで72Bモデルを超えられる理由は？

(1) 3D-Resamplerによる極端なトークン効率化がLLMの処理負荷を削減し、計算リソースを推論品質に集中できる。(2) 統一文書学習がノイズのないクリーンな教師信号を提供する。(3) ハイブリッドRLが学習効率を最大化する。(4) 高品質なデータキュレーション（STEM、Long-tail、Long-CoT）が小さいモデルの能力を最大限に引き出す。

### Q8. 事前学習の3段階はなぜ必要なのか？

段階的に学習可能なパラメータを増やすことで、安定した学習を実現する。Stage 1でResamplerのみを学習し、視覚-言語の初期アライメントを確立。Stage 2で視覚エンコーダを開放し、知覚基盤を強化（LLMはフリーズのまま、OCRリッチデータの流暢さの問題を回避）。Stage 3で全パラメータをEnd-to-Endで学習し、最高品質のデータで全能力を統合する。

### Q9. GRPOのハイパーパラメータ設定は？

- バッチ: 128プロンプト × 8応答/プロンプト
- 最大応答長: 8192トークン
- 温度: 1.0
- 長い推論モードの割合: 50%
- KL損失: なし、エントロピー損失: なし（安定性重視）
- 学習率: 1e-6（固定）
- 報酬: `R = R_acc + R_format + R_rep + 0.5 * R̃_rm`

### Q10. 推論時の効率性は具体的にどの程度か？

OpenCompass（画像タスク）: 8.7Bパラメータで77.0のスコアを **7.5時間** で達成（GLM-4.1V 10.3Bの17.5時間の42.9%）。VideoMME（動画タスク）: 73.5のスコアを **0.26時間**・**28Gメモリ** で達成（GLM-4.1V: 2.63時間・32G、Qwen2.5-VL 7B: 3.00時間・60G）。この効率は主に3D-Resamplerによる視覚トークン削減によるもの。

---

## まとめ

MiniCPM-V 4.5は、以下の3つの核心的改善により、8Bの小型モデルで大規模モデルを凌駕する性能と効率を実現した：

1. **統一3D-Resampler**: 画像16倍・動画96倍の圧縮。画像と動画で重みを共有し、知識転移を促進
2. **統一文書学習パラダイム**: 動的ノイズ付与でOCR・知識獲得・文脈推論を統合。外部パーサー不要
3. **ハイブリッドRL**: 短い/長い推論モードの相互強化。学習効率とモード制御性を両立

**推奨設定:**
- 画像理解: `max_slice_nums=9`, `query_nums=64`
- 動画理解: `max_frames=1080`, `fps=10`, `pkg_size=6`
- 短い推論: 通常のプロンプト
- 長い推論: `<think>` プレフィックス付きプロンプト
